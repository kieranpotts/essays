I've spent much of 2026 rethinking how I work. This post is a snapshot of where I'm at now. New models, harnesses, and tools arrive every day, but the broad categories they fall into look increasingly stable. Meanwhile, my new ways of working are settling into a consistent pattern. So it's time to do a write-up.

It has been fun. AI has revived my love of programming. I no longer work alone on my pet projects. Even when I'm working solo, it feels like collaboration. It's a less lonely craft.

Plus, I can onboard into unfamiliar problem spaces and existing codebases much faster than I ever could before. And it is easier to learn new languages, and get better at familiar ones, on-the-job. (I'm loving getting to know Kotlin right now!)

I made one assumption at the start of this journey, which is that getting the most out of AI tools will require doubling down on classic engineering methods — not discarding them. Well-defined requirements, considered architectural trade-offs, construction in small increments, iterative design, automated tests, and plentiful feedback loops and decisions grounded in data — not least real-world user experience of working software. I expected AI to displace none of these, and I designed by AI-assisted development workflow accordingly.

This assumption has held true. If anything, evergreen principles of good software engineering carry more weight than ever. Structured engineering practices produce structured artifacts that provide valuable knowledge to LLMs via context. The better the written record of a system, the better the agent's work, because an agent can only act on what it's been given.

The rest of this post is about how I put this into practice.

== My current AI toolkit

I work in two modes, with a different toolkit for each.

For at-keyboard work I mostly use {link-claude-code}[Claude Code] in VS Code, Zed, or the terminal. This is synchronous work. I give an instruction, watch what the agent does, approve changes, and steer through follow-up prompts. I'm manually managing the agent loop and the context. This is my default way of working for high-level design and for anything ambiguous, where the solution is hazy or the outcome depends on human judgment.

Even with real-time oversight, I want to keep agents isolated from my host system. So I always open my code repositories in a devcontainer (which I also load Claude Code CLI into). Only my workspace directory is mounted from the host, not the rest of my home directory, and agents run as a non-root user. There is no Docker in the container and no route to the host's Docker daemon, since access to that amounts to root on the host.

Previously, I had locked agents out of using Git inside the container. I would review all changes from the dirty working tree before committing myself from the host. I've relaxed this, recently. I now use `AGENTS.md` files to instruct agents _not_ to commit anything, and they mostly follow that rule. Where they do not, it's an easy job to revert the revision if I'm not happy with it. It is more convenient for me to commit from inside the container, but a consequence is that I now mount my `~/.ssh` directory into the container. It's read-only, but I make sure the mounted private key is used solely for GitHub/GitLab authorization — in case it should be compromised. There's some risk here, and I would not do this for commercial projects. My GPG signing key stays on the host, at least — the container only uses the host's `gpg-agent` and a copy of my public keyring.

I always work in a devcontainer. There is one container for my whole personal workspace, with every repository mounted into it. Agents run inside that container as a non-root user. There is no Docker in there, because access to the host's Docker daemon amounts to root on the host.

All of my repositories are now checked out as Git worktrees: a bare clone, with one working tree per branch alongside it. A piece of work can be given a checkout of its own without disturbing any other.

But Claude Code does a lot behind the scenes to manipulate the context, which makes it a poor foundation for stable, repeatable workflows. That is one reason I do not use it for background, away-from-keyboard work, which suits tasks that are more predictable, such as producing code to a well-defined design.

For work that runs in the background I use {link-pi}[Pi], in a terminal multiplexer — I've been switching between tmux, Zellij, and Herdr. In Pi I almost exclusively use xref:garden::open-weight-model.adoc[open-weight models], both hosted and local, running in {link-ollama}[Ollama]. Background tasks are not entirely unattended. They're running in another pane, which I keep an eye on, and I always verify the outputted artifacts.

== Coding agent harnesses

As an industry, we're still figuring out what a good coding agent harness looks like. At one end are minimal frameworks like Pi. At the other are harnesses that orchestrate swarms of highly autonomous agents. I've looked at Codex CLI, AMP, Factory Droid, and OpenCode too. OpenCode, which is fully open source, is an excellent choice if you want something that just works out-of-the box. I used it a lot early this summer. But I eventually settled on Pi for its flexibility.

Pi is a minimal coding agent. It is closer to a framework for building your own harness than a finished product. Its motto is to adapt the coding agent to your needs, not the other way around. It is built on the principle that we should be able to modify our own agentic workflows.

Right now I want to experiment with ideas quickly, so a minimal, extensible core suits me.

Pi's system prompt is under 1,000 tokens, against about 10,000 for Claude Code, and that default prompt can be extended or replaced entirely. Tools, commands, events, and interface components can all be extended, too, and bundled into packages that hot-reload. By design there is no MCP, no subagents, no plan mode, no background bash, and no built-in to-do list — but there's a large registry of third-party packages that add all these things, or you can quite easily ask a capable model to write your own extensions.

Out-of-the-box, Pi also has no security controls at all. This is deliberate. Most agents ask the user to approve each action, but that is a false economy, because people turn the prompts off or keep blindly pressing "`accept`". Pi's philosophy is that containerization should be the basis for protecting your systems from a malicious or compromised agent, with a permissions gate added to suit your own risk appetite.

So I have written {link-pi-extensions}[my own extensions] for it. Two of them are permission gates, built for at-keyboard sessions where I am watching each step. They share one rule: when in doubt, ask, and if nobody answers, deny.

The first, `tool-gate`, asks for confirmation before any tool call that changes something, such as a write, an edit, or a move. It also asks before any call that touches a file that looks like a secret, such as `.env` or a private key, even if the call only reads it. A timeout, or a session with nobody there to answer, counts as a no.

But Pi's `bash` tool can do everything the other tools can, and a gate that inspects tool names and file paths cannot see inside a command string. `cat > src/index.ts` is a write, and `curl -d @.env` is exfiltration, yet neither looks like one. So the second, `command-gate`, replaces `bash` with a runner that never invokes a shell. Pipes, redirects, and chained commands are rejected outright, since without a shell they could not work anyway. A short list of read-only programs, such as `ls`, `cat`, and `grep`, runs unprompted. Anything else is put to me first, and so is any command that names a secret file, even if the program is `cat`. Language runtimes such as `node` and `python` are deliberately kept off the allowlist, because `node -e` can do anything at all.

Neither gate is a security boundary. Both run inside the agent's own process, and both recognize secrets by filename, not by content. The container is the boundary. The gates are there to keep me in the loop while I am watching.

The third extension, `role-switcher`, solves a different problem. Out of the box, Pi has a single identity: an expert coding assistant. That is the right persona for writing code and the wrong one for most of the work around it. Ask it to specify requirements and it hands back an implementation plan. Ask it to review a change and it rewrites the change. So the extension swaps Pi's system prompt for a named role — product manager, software architect, programmer, code reviewer, and so on — picked from a menu, mid-session. Each role is a Markdown file, which can also declare the model, thinking level, and tools the role is allowed. The analysis roles get read-only tools, because a reviewer that cannot rewrite the code it is reviewing is a better reviewer.

== Away from keyboard

For work that is truly xref:garden::away-from-keyboard.adoc[away-from-keyboard] I have been building {link-genie}[Genie]. The gates I described above assume that somebody is there to answer them. When nobody is, a prompt can only time out and deny, and a gate inside the agent's own process is the agent policing itself. So Genie takes a different approach. It does not ask the agent to behave. It takes away the means to misbehave, and it records everything that is left.

Genie wraps Pi in a hardened container, and wherever it can, it puts the controls in a different process from the agent.

image::diagrams/genie-architecture.svg[opts=inline]

The container is the first layer. Pi starts with all of its built-in tools switched off, so there is no `bash`, no `read`, and no `edit`. There is nothing to fall back on, either, because the image contains no Git, no `curl`, no `wget`, and no `ssh`. The agent runs as a non-root user, with every Linux capability dropped, a read-only root filesystem, and limits on memory and processes. The container sits on an internal Docker network with no default route to the outside world. Even DNS does not resolve.

The agent's only route to the project's files is through xref:garden::model-context-protocol.adoc[MCP]. A single extension, `mcp-client`, gives it eight filesystem tools: read, list, search, write, edit, move, create a directory, and one that tells the agent where its project root is. Each call goes to a gateway, which checks it against a tool allowlist and passes it to a filesystem server, in a container of its own. The server confines every path to the one project directory, so a read of `../etc/passwd` is refused in a process the agent cannot touch. The project is mounted into the agent's container too, but read-only, for me to browse. The agent has no tool that can reach that mount. The filesystem server holds the only writable handle on the project.

There is one privileged component in all this. The gateway starts the filesystem server, so it holds the host's Docker socket, and access to the Docker daemon amounts to root on the host. That privilege is confined, not removed. The gateway is not reachable from outside the stack, and the agent can reach it only by making MCP calls.

The agent's only route to a model is through a LiteLLM proxy running on the host. The proxy holds the API keys, so they never enter the container, whether as environment variables, as config files, or baked into the image. It also routes requests by role, which I will come back to.

Two more extensions run inside Pi. `secret-sentry` refuses any call that names a file that looks like a secret, such as `.env` or a private key, with no approval path. It also scans tool output for values that look like secrets, such as private key blocks and API tokens with a known prefix, and swaps them for a placeholder before the model sees them. That covers the case the filename rule misses: a key pasted into an ordinary file. `audit-log` records every tool call and what it actually did. It marks each turn, so every call can be traced to the instruction that caused it. And it records the shape of every model request, meaning which model, how many messages, and how many bytes, but never the content. Like the gates, both extensions run inside the agent's process, so they are defense in depth, not a boundary.

There are no approval prompts. Writes go ahead unprompted, and are logged like everything else. A prompt with nobody there to answer it is theater, not a control. The audit trail stands in for my attention.

Driving it is deliberately dull. A `genie` command on the host takes a prompt and prints the agent's response to standard output, so it composes with ordinary shell scripts. It scopes the agent to the current project directory, and it refuses outright to scope it to `/` or to my home directory, which would put my keys and every other repository inside the boundary.

That is a lot of capability traded away for accountability. The agent cannot run the tests, build the project, install a dependency, or check out a branch. It reads and edits files, and nothing else. The trade only pays when nobody is watching. When I am at the keyboard, I am the control, and I would rather have an agent that can run the test suite. Genie is still a work in progress.

== The AI-driven software development lifecycle

The most important parts of a structured lifecycle are the seams between its phases.

Every phase consumes an artifact and produces another. Analysis produces a specification. Design consumes that specification and produces design docs and decision records. Planning consumes both and produces a delivery plan, broken down into small increments. Construction consumes one increment at a time.

Human teams get away with fuzzy seams, because people fill in the gaps by talking to each other. Agents cannot. An agent starts every session knowing nothing about the project. Whatever is not written in the artifact it is handed does not exist, as far as that agent is concerned.

So the inputs and outputs at each seam must be well defined. I have built a set of template repositories for exactly this purpose:

* *{link-tpl-specs}[Specs]*: what the system does, in business terms.

* *{link-tpl-rfc}[RFCs]*: how significant technical decisions were made, and why.

* *{link-tpl-design}[Design docs]*: what the system looks like in production.

* *{link-tpl-plans}[Plans]*: when, and in what order, the work gets done.

* *{link-tpl-audits}[Audits]*: point-in-time evaluations of the as-built architecture.

* *{link-tpl-risks}[Risks]*: the security and privacy risks the system carries.

Each one is a version-controlled store with a defined lifecycle. A proposal to change the requirements, for example, moves from draft, to proposed, to accepted, to released. Each store ships with small skills that drive those state transitions.

Sitting above the stores is my {link-skills}[collection of agent skills], which covers the phases of the lifecycle itself: specify, design, plan, code, test, review, and so on. The skills are harness-agnostic: they describe how I want the work done, not which product is doing it, so the same workflow carries from one agent to another without being rewritten. They are also deliberately independent. No skill hands off to another. The stores are the persistence layer between them. An agent working on an upstream step writes an artifact to a store, and an agent working on a downstream step — a different session, perhaps a different model — reads it as xref:garden::context.adoc[context] for its own task.

Because the stores all live in Git, requirements, decisions, designs, plans, and code are branched, committed, reviewed, and merged in exactly the same way. Auditability and rollback come for free.

== Documentation is the context

xref:garden::documentation.adoc[Documentation] is the key to all of this.

If everything is written down in a durable artifact, in a structured and consistent way, including the architectural designs and the decisions behind them, then it all becomes high-quality context for agents. xref:garden::context-engineering.adoc[Context engineering] turns out to be mostly a documentation problem.

In 2024 I made xref:rfcs.adoc[the case for RFCs and decision logs]. The argument then was about people: a decision log records _why_ a system is made the way it is, so that knowledge survives after the original decision makers have moved on. That argument now applies with even greater force. An agent is the ultimate new starter. It joins the project with no history, every single session, and it reads everything you give it.

Nearly every repository of mine now has an `AGENTS.md` file at its root. It describes the project's structure, tools, and rules, and it points to the technical standards that govern the work, each with a note on when to consult it. Agents fetch the detail on demand, when the task calls for it.

There is a deeper shift here, too. I now treat the specification — not the code — as the xref:garden::single-source-of-truth.adoc[source of truth]. When the behavior of a system needs to change, the change starts in the spec. The code is derived from it. This is the idea behind xref:garden::spec-driven-development.adoc[spec-driven development]. I subscribe to it, with two caveats. The first is about how it is practiced. The second I will come to later.

Spec-driven development, practiced naively, is agentic waterfall: write a big specification, then have an agent generate all the code in one go. A related teaching, that when the code is wrong you never debug it but go back and fine-tune the spec, is vibe coding by a different name. What I practice is _fine-grained, iterative_ spec-driven development. It is big design up front, but with feedback loops, and the work is delivered in small increments. Agents help me move through those cycles quickly. The steps are still disciplined and deliberate.

== Owning every commit

The other half of my approach is the environment the agents run in.

Inside the devcontainer, agents are locked out of Git. They cannot stage, commit, or push. The end state of any agent's task is a dirty working tree, and nothing more.

I do the committing myself, from the host. I review the changes in the working tree, as a diff, and then I decide what goes into the history and under what message.

This is the control that matters most to me. Everything committed in my name, I own. xref:garden::accountability.adoc[Accountability] cannot be delegated to a tool, so the act that confers it stays with me.

== Reviewing everything, for now

Earlier I mentioned two caveats about treating specs as the source of truth. This is the second.

In theory, if the acceptance criteria in a specification are executable, then passing tests tell you the software is correct, and nobody needs to read the code. I am not there yet. I still review all output, and I am not ready to rely on executable specifications alone.

That will change by degrees. As my trust in these tools and ways of working grows, backed by a track record, I expect to spend less time on review.

But I think I will always do some. A test suite demonstrates behavior. It says very little about structure. Whether a change introduces threads, for example, and whether it uses them safely, is an architectural concern that tests are bad at exposing and that is expensive to get wrong. Those are the decisions I expect to keep reviewing for myself.

== Engineering, only more so

Effective use of AI in software development requires doubling down on age-old engineering practice. Clear requirements. Considered design. Small, incremental changes. Automated tests. xref:garden::version-control.adoc[Version control]. Review. None of this has been displaced. All of it now carries more load.

The reason is volume. Agents produce changes faster, and in far greater quantity, than any human team can. Everything that keeps a codebase trustworthy has to scale with that output, or the codebase stops being trustworthy.

Code is cheap now. Bad code is not. It may be hard to change, and it may carry real business risk. And the code in front of me may not have been written by a human at all, so I trust it even less. That is why I do not want a massive changeset to review, or a big-bang deployment to manage. I want a delivery pipeline of small increments toward a bigger goal. Just because an agent can generate a mountain of code from a single prompt does not mean it should.

So my process has become more structured, not less. I now work through an explicit development lifecycle — analysis, design, planning, construction, testing, review — with each phase run as a discrete step. This is not a return to xref:garden::waterfall-model.adoc[waterfall]. The steps are small and the whole cycle is repeated for every increment. But each step is distinct, with a defined purpose, a defined input, and a defined output.

Fred Brooks would recognize the shape of this. As I wrote in xref:mythical-man-month-50.adoc[my review of _The Mythical Man-Month_], the hard part of software has always been deciding precisely what to build, not typing it in. A model that generates code in seconds makes that old truth more obvious than ever. The core of the craft is learning about a problem and then creating software to address it. Writing program code has not been the core of it for a long time.

== Where judgment stays human

Some parts of the lifecycle I do not hand over.

The first is discovering the problem. Understanding what the client or the business really needs is a human-centric activity, a kind of behavioral engineering that depends on conversation. I do not chain agents together for this phase. Agents can help at the edges, for example by reviewing the language I use for consistency with the business's terminology, but the understanding has to be mine.

The second is architectural design. This calls for _good taste_, and I do not want to rely on an agent's choices. Frontier models are increasingly good design partners. I ask them for a menu of options, each with its trade-offs, and then I choose. Ultimately we are designing products for ourselves, and only humans understand what humans need.

== Try not to write anything

A key principle follows from all of this: try not to write anything.

The only things I should be writing by hand now are the artifacts that control agents. Birgitta Böckeler {link-bockeler}[sorts these into two categories]. _Guides_ steer an agent before it acts: the `AGENTS.md` files, skills, technical standards, and permission rules. _Sensors_ check an agent's output after it acts: tests, linters, type checkers, validation scripts, and review.

When an agent gets something wrong, the temptation is to fix the output myself. It is nearly always the wrong move. A hand-made fix corrects one mistake, once. The better response is to ask what was missing. Was it a gap in a guide, so the agent did not know the rule? Or a missing sensor, so nothing caught the mistake? Close that gap and the same mistake is prevented in every future session.

Underneath, this is a question about feedback: how does an agent learn about the quality of its own work? The objective is for agents to produce code the way _I_ want it produced, consistent with my policies and rules.

My repositories are slowly accumulating these controls. The skills collection has a validator script that every skill must pass. This blog has a CI check that fails if a post's date cannot be parsed. Each one captures a failure that happened once, and should not happen again.

I still make small changes by hand after review, but I try to treat each one as a signal that a guide or a sensor needs work.

== Never trust an agent

My general principle is not to trust agents. They must never be fully autonomous. They should operate only in tightly controlled environments, inside xref:garden::guardrail.adoc[guardrails] that are enforced by the environment and not merely requested in a prompt.

This is not cynicism about the technology. A model's output is non-deterministic. An instruction in a prompt is a request, which the model may misread, forget, or reason its way around. A permission rule enforced by the harness is a fact.

No matter how capable models become, they cannot be trusted in the way we trust a traditional program. Their guardrails are learned from training data, not enforced by hard-coded logical conditions, so they hold _most_ of the time, not _all_ of the time. For a great many uses, "`most of the time`" is not good enough.

That includes the guides I lean on so heavily. Skills, rules, and instructions are really just prayers, not deterministic quality gates. They save me typing, but an agent can ignore them, as it may when its context window gets bloated. Reviewer agents that double-check the work of other agents improve outcomes, but they do not solve the problem either. I am still relying on agents to produce good output, and I have added a layer of orchestration complexity without getting stable results.

On security, the key idea for me is Simon Willison's {link-willison}[lethal trifecta]. An agent becomes dangerous when it has three things at once: access to private data, exposure to untrusted content, and the ability to communicate externally. With all three, a xref:garden::prompt-injection.adoc[prompt injection] hidden in a web page can instruct the agent to read your secrets and send them to an attacker. With any one of the three removed, that attack does not work.

You cannot make prompt injection impossible. You can only xref:garden::lethal-trifecta.adoc[break the trifecta]. My preference is to remove web access from any agent that runs in the background. When I am at the keyboard, I am the control. When I am not, the agent gets no route to the outside world.

== Deterministic wrappers

An agent harness, the software that gives a model access to tools, files, and networks, cannot rely on the model to police itself. It needs ordinary programs, built from logic, wrapped around it to constrain what the model is actually permitted to do. The reliable part of the system is the part that _isn't_ the model.

So every model request from my workspace passes through a central point of control, which applies security and governance deterministically:

* Traffic is locked to an allowlist of approved models and providers.

* Each key has a spend limit, so a runaway loop cannot run up an unbounded bill.

* Zero data retention is enforced with the providers I use.

* Prompt injection is blocked, by screening against more than 30 attack patterns derived from OWASP.

* Personally identifiable information is redacted before it ever reaches a provider.

None of these is an AI capability. Every one is a deterministic control wrapped around a non-deterministic core. And because these checks run in separate services, completely isolated from the agentic workflows, they also free the agents to get more work done.

That, to me, is the real shape of building responsibly with AI: not trusting the model more, but architecting so that I need to trust it less.

== A team of specialists

Working with agents has turned out to be closer to managing people than I expected. I now have a small team of junior developers, testers, reviewers, and technical proofreaders. Some are little more than rubber ducks. Some I delegate work to, always with oversight. Each has its own personality, and all of them are equally over-confident in their abilities.

I keep them small and specialized, in line with the single responsibility principle. Each has clear boundaries, a persona such as software tester, and a role it is expected to fulfill. Narrowing an agent's scope limits its freedom to wander, which also reduces the probability of hallucination. This mirrors the structure of a human team, with each agent focused on one part of the lifecycle. But a team of agents is still a team of agents. It improves outcomes without becoming a quality gate, which is why it sits alongside the deterministic controls described above and does not replace them.

== The least capable model

It is tempting to turn to the most powerful model for every task. I aim for the opposite: to run the _least_ capable model that can do the job, which is to say the cheapest.

This is only possible because of everything described above. Work is still broken down into small, incremental chunks. A small, well-specified task, supplied with good context, is within reach of a modest model running on my own machine. A large, vague one will defeat even a frontier model.

So model choice is made per step, not per project. Each of my skills notes the class of model I recommend for it. And in Genie, requests are routed by role — programmer, technical lead, technical writer, security analyst — with each role mapped to a different local model.

The least capable model is not always a small one. The judgment-heavy checks described below, such as architecture audits, threat modeling, and reviewing a design against its intent, are the work where frontier models earn their cost. Small, well-specified construction tasks are where a modest local model is enough. The aim is to match the model to the step, not to avoid frontier models altogether.

There is a human in the loop between each step. I am removing those checkpoints, slowly, one at a time, and only where the outcomes have been consistently good.

== Stability, not only throughput

Most of the conversation about AI in software is about speed. But the {link-dora}[DORA research] has long measured delivery performance on two axes: xref:garden::throughput.adoc[throughput] and stability. Faster is only better if you are not also breaking things more often.

I do not think raw throughput is where the real value of these tools lies. Raising the output of one station on a production line does not raise the output of the line. It relocates the bottleneck, and grows a pile of work-in-progress in front of whatever the new constraint turns out to be. In software development the constraint has not been the typing for a very long time, probably not since the arrival of high-level programming languages. The constraint is everything that surrounds the typing: agreeing what to build, deciding how to build it, reviewing it, testing it, getting it approved, and getting it released.

Most of us still work under Scrum-like processes that are, in truth, incremental waterfall. Few teams, in enterprise contexts anyway, practice genuine agile software development. Code that appears instantly still waits for the next refinement session, the next review, the next regression cycle, the next change advisory board, the next release window. Generate code ten times faster and you do not get working software ten times sooner. You get a longer queue.

The real value lies in the quality of what we produce: the robustness, reliability, security, and performance of our systems. To see why, look at what we have historically been able to automate. Before AI, the only quality checks we could automate were those that could be reduced to deterministic rules: static code analysis, type checking, schema validation, the execution of runtime behavioral tests. These are enormously valuable, but they can only answer questions that somebody has already worked out how to express as a rule.

The checks that matter most are not like that. Does this abstraction earn its keep? Does this design document still describe the system it claims to describe? Has this change widened the attack surface? Is this the third time we have solved the same problem, slightly differently, in three different places? Does this specification actually describe what the customer needs? These are questions of judgment, opinion, taste, and context. There is no rule to encode. They can be answered only by inference, by somebody reading the thing and forming a view.

Until now, that somebody had to be a human being, which made these checks expensive. And because they were expensive, we rationed them: a design review, a pre-release threat modeling workshop, an annual architecture audit. They were occasions, not habits. When a deadline loomed, they were the first thing cut. Every methodology we have adopted includes them on paper, and hardly any team has sustained them in practice.

It turns out that frontier models, given good guides, are rather good at this kind of work. That is the development worth paying attention to. Not that the cheap part of software development has become cheaper, but that the expensive part has become affordable. We can now configure agents to:

* Review code changes against the project's standards, conventions, and architectural intent, not merely against its linting rules.

* Run threat modeling workshops on a far more regular cadence than a human-only team can sustain.

* Catch drift between the evolving implementation and the architecture and design documents, keeping the architectural artifacts synchronized with reality.

* Interrogate requirements for ambiguity, unstated assumptions, and missing acceptance criteria, before any code is written.

* Generate proposed architectures from requirements specifications, with the options considered and the trade-offs between them made explicit.

* Decompose designs into small, incremental units of delivery, feeding backlogs and supporting continuous integration.

* Audit a codebase for structural drift, such as shallow abstractions, tangled dependencies, and repeated patterns, and report back a prioritized set of remedies.

* Triage incoming issues, reproducing reported defects and classifying them ahead of human review.

* Validate delivered software against what users actually need, rather than only against the acceptance criteria that were agreed up front.

Not one of these is a new idea. Every one is something we already knew we ought to be doing. What has changed is that they no longer need to be rationed. They can run on every change, at a cadence no team could afford to staff. Several of my skills exist for this purpose and produce no feature code at all.

There is an important caveat. An inferential check produces findings, not decisions. It hands me a set of candidate problems to accept, reject, or defer. And its judgment is itself probabilistic: run it twice over the same input and it may not say the same thing twice. So it must not become a gate that passes or fails a change on its own, and it must not displace the deterministic checks. Anything that can be expressed as a rule should still be expressed as a rule, and enforced mechanically. Inference is for widening the net, not for replacing the mesh.

Nor does any of this take the human out of the loop. It moves them. The work is no longer performing every check but deciding which of the findings matter. That is a far better use of an experienced engineer than reading a diff line by line. It is also work that models remain conspicuously bad at, because it depends on what they lack: knowledge of why the system came to be the way it is, of how much change the organization can absorb, and of which risks are worth carrying.

So if you measure these tools by how much code they emit per hour, you are measuring the wrong station on the line. The interesting question is not how much faster we can write our software. It is how much better we can now afford to make it.

== Loops and runners

Not every experiment has stuck.

The logical next step from all this is xref:garden::loop-engineering.adoc[loop engineering]: a platform that runs a whole workflow by itself, chaining agent steps together with deterministic ones. On such a platform the committing would be done deterministically, by a scripted step, and not left to an agent's discretion.

I built an experimental one of my own. It ran workflows defined in YAML: ordered pipelines of script steps and agent steps, with typed outputs passed between them, limits on turns and time, and a state file so that a failed run could be resumed. I have abandoned it for now, because I do not currently have a use case that justifies it. That may change.

I have also had success using a self-hosted GitHub Actions runner to trigger agentic tasks on my own workstation. A workflow is dispatched from the command line with a prompt, the agent runs locally in a container, and the output comes back as a workflow artifact. I am not using this at the moment, either, but I will return to it for a commercial project I am working on.

== What the engineer is for

For decades, the developer's primary interface with the machine has been syntax: curly braces, type annotations, and the grammar of high-level programming languages. Agentic software development is a new paradigm, in which programming happens at a higher level of abstraction. It is structured, executable English. The human provides intent, architecture, and judgment, captured in artifacts: instructions, specifications, designs, plans. These are written precisely enough for an agent to act on, and for a human, a script, or another agent to verify against. The machine translates that intent into working software.

Product engineering has always worked at a higher level of abstraction than syntax. Now it is easier to stay at that level, without context switching into low-level concerns. I no longer need to remember all of Java and Spring's APIs, or every AWS service. I delegate the low-level code to agents, and I review it. I just need to know the fundamentals.

Expertise shifts toward _evaluating_ code and _orchestrating_ its construction. How reliable is it? Is it secure? Will it scale? Answering those questions takes a deep understanding of how systems work. So the skills I think are worth investing in now are computational thinking, critical thinking, systems thinking, AI literacy, problem solving, and the ability to evaluate outputs.

The job is no longer to write lines of code. It is to understand the whole architecture and the trade-offs made in its design.

== What comes next

Handing work over to agents is an incremental and experimental process. I give them a little more to do, watch the outcomes, and adjust. If a workflow stops producing good results, the human checkpoints go back in.

New models arrive constantly, and I experiment with them continuously. Public benchmarks are a useful first filter, but they say little about how a model performs on my own work. So I will soon add xref:garden::ai-eval.adoc[evals]: a suite of tests that lets me judge the capabilities of a new model myself, against my own collection of skills. Then the question of which is the cheapest model that can reliably run a given skill becomes one I can answer with evidence.

== Conclusion

The pattern across all of this is that AI has pushed me back toward fundamentals. Clear requirements, written-down decisions, small increments, tests, review, and a human who is accountable for every commit. The agents do more and more of the typing. The engineering is still mine to do.

That is where I am, so far. I expect to be somewhere else in a year.
